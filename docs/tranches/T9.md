## 3. Choix de découpage
1. **Un spike d'abord, S10 « hôte webview »** (`fr-t9-hote-spike`, Opus, LOCAL : GPU réel, vraie souris, vrai
   clavier, échelle 125 / 150 %) : S2 a laissé non mesurés le suivi de position au défilement, le rognage
   (`SetWindowRgn`), le focus et la saisie réels, le DPI, la minimisation, la mémoire par popup, le réseau sortant,
   et la capture pour le harnais pixels. Il tranche aussi : **page de premier niveau ou iframe sandboxée dans une
   page hôte** (S2 §2 : seule l'iframe sans `allow-same-origin` rend `localStorage` inaccessible et coupe la page de
   `window.ipc`, comme le test d'isolement l'exige). Livre `docs/spikes/S10-hote-webview.md` et
   `docs/decisions/ADR-019-hote-webview.md` (périmètre `unsafe`, dépendances, capture). Toute la chaîne native en
   dépend ; les modèles purs non.
2. **Socle T9** (`fr-t9-socle`, léger, le chef en moins de 10 minutes) : coquilles des modules ci-dessous,
   dépendance de chemin `fragment-ui` → `fragment-html`, lignes de `scene.rs`. AUCUNE dépendance externe : c'est
   `fr-t9-hote` qui les ajoute, après l'ADR.
3. **Modules posés par le socle** : `fragment-html/src/{hote,protocole,pont,theme_page,capture}` ;
   `fragment-ui/src/{vue_hebergee,embed,md_embed,vue_image,vue_html,html_surface,chat_origine}`.
4. **Le pont est un script ÉCRIT pour ce dépôt** (`fragment-html/src/pont/pont.js`, embarqué par `include_str!`),
   jamais traduit de `htmlBridge.ts` : il part de `pont-minimal.js` et suit le CONTRAT des messages (noms, champs,
   versions `tv` / `lv`), que décrit son module Rust (`MessagePont`, sérialisation, filtre `fragmentHtml`). Le texte
   aplati du script est jugé contre `flatten_page` (Rust, déjà porté) sur les mêmes fixtures.
5. **Les calques AU-DESSUS de la page** (surlignages, passage révélé) : un HWND WebView2 recouvre GPUI (S2 §6.0) ;
   ils sont donc PEINTS DANS LA PAGE par le pont (message `highlights` : rectangles, la couleur de `.range-highlight` de
   Fragment, accent translucide, lue dans `docs/constantes-rendu.md`), comme S2 (c) le propose. La marge et ses widgets sont À CÔTÉ de la
   page (la page se réagence dans les 3/4) : GPUI normal. Les menus qui recouvrent la page sont des fenêtres GPUI
   (S2 E2b). Décision à confirmer dans ADR-019 (question au chef, §7.2).
6. **Le cadre commun est générique** (`embed/`) et ignore la webview ; l'embed d'une page HTML
   (`fr-t9-embed-html`) est la seule tâche qui marie le cadre et un popup qui défile et se rogne avec son hôte.
7. **En Opus** : le spike, `fr-t9-hote` (fenêtre native, `unsafe`), `fr-t9-html-surface` (géométrie asynchrone,
   versions, `mapPos`), `fr-t9-embed-html` (popup suivi image par image, rogné, molette rendue à l'hôte).
8. **Dépendances vers T4, T5, T7** (posées sur les tâches, pas sur l'épic : Beads propage le blocage d'une épic) :
   `fr-t9-vue-html` → `fr-t5-montage-note` (montage des calques sur une vue à surface) ; `fr-t9-origine` →
   `fr-t7-vue` ; `fr-t9-montage` → `fr-t5-montage-pdf`, `fr-t7-montage` ; `fr-t9-livraison` → `fr-t7-livraison`
   (fichiers `pixels/tranches.json`, `cliquet.json`).

**Le webview se capture-t-il par le harnais ? Pas tel quel.** `render_to_image` ne voit pas un HWND (S2 §5), et le
popup est une autre fenêtre. Méthode retenue (à valider par S10, tâche `fr-t9-capture`) : le harnais
`fragment-pixels` rend la fenêtre GPUI comme aujourd'hui, puis, pour chaque webview vivante, demande à WebView2
une image de SON contenu (`ICoreWebView2::CapturePreview`, PNG, attendue avant la capture ; repli :
`PrintWindow(PW_RENDERFULLCONTENT)` sur le popup) et la compose dans le framebuffer à son rectangle, rognée par
la même région que le popup. Ce qui est jugé : la géométrie du popup (position, taille, rognage) en strict, et le
rendu de la page par le moteur Chromium de WebView2 contre celui d'Electron. ★ Les deux Chromium n'ont pas la même
version : un écart d'anticrénelage du texte DANS la page est de la même famille que la dette des glyphes
(ADR-009), à chiffrer, pas à masquer. Déterminisme : pages sans animation, polices de l'app passées en octets par
le pont des deux côtés (DM Sans), attente du message `layout` avant capture. Côté Fragment, Playwright capture
l'iframe avec la fenêtre (mode invisible, verrou de capture).

## 7. Risques et questions au chef
1. **Dépendances externes nouvelles (QUESTION)** : en production, `lb-wry =0.53.3` (paquet de Longbridge, le wry
   de `gpui-webview` ; MIT / Apache-2.0) et probablement `webview2-com` (MIT, déjà au lock par wry : contrôleur,
   `CapturePreview`, `WebResourceRequested`) et `windows` en direct (FFI du popup : `CreateWindowExW`,
   `SetWindowPos`, `SetWindowRgn` ; « autorisé via gpui » par program.md, l'usage DIRECT est à confirmer).
   `gpui-webview` lui-même ne sert presque à rien sous Windows (S2 condition 1) : le garder ou non est à trancher.
   Aucun fork (plafond de 2 atteint, ADR-017).
2. **`unsafe` (QUESTION → ADR-019)** : la FFI Win32 du popup possédé et le `HasWindowHandle` du parent ne
   s'écrivent pas sans `unsafe`. Proposition : `unsafe` confiné à `fragment-html/src/hote/win32.rs`, chaque bloc
   commenté (`// SÛRETÉ :`), aucune autre crate. Également : peindre les calques DANS la page par le pont
   (§3.5) au lieu de fenêtres GPUI par-dessus.
3. **Isolement** : une page de premier niveau atteint `window.ipc` et son `localStorage` ; le test d'isolement de
   `html-view` exige l'inverse. L'iframe sandboxée dans une page hôte (parité) est à mesurer par S10 ; sinon,
   divergence à remonter.
4. **`image-embeds` (QUESTION)** : aucune tranche ne la porte (program.md §5) ; `imageEmbed` est une des deux
   fabriques d'`embedRegistry` et la vue image n'existe pas. Proposée dans T9 (`fr-t9-image`).
5. **WebView2 runtime et licence** : le runtime Evergreen est présent sur Windows 10 / 11 ; son
   redistribuable (amorceur Microsoft) n'est à embarquer que si l'installeur doit le poser — à noter pour la
   livraison du binaire. Pages sur un runner sans GPU : S2 a vu WebView2 peindre sur `windows-latest`.
6. **Pixels de la page** : Chromium de WebView2 ≠ Chromium d'Electron (§5) ; si l'écart de texte dans la page
   dépasse le sas d'ADR-009, chiffrer et remonter (aucune tolérance nouvelle sans le chef).
7. **Popup qui défile avec son hôte** (`fr-t9-embed-html`) : suivi à chaque image, rognage par le viewport de
   l'éditeur ou du fil, sous les barres et menus ; une image de retard se voit. Si S10 mesure un retard visible,
   repli à décider : l'embed INACTIF montre la dernière capture (`CapturePreview`) peinte par GPUI, le popup vivant
   n'apparaît qu'à l'activation (perte : l'animation ne joue pas tant que le cadre est inactif — divergence).
8. **`fr-zdx`** (iframe vivante, animations CSS, SMIL complet, anticrénelage SVG, CSS hors sous-ensemble dans le
   Markdown) : elle reprend la machinerie de `fr-t9-embed-html` pour des BLOCS ; ADR-012 §5 refusait une webview
   par bloc (N popups, mémoire). Lourde : à redécouper perte par perte quand elle sera prête, chaque perte fermée
   par une scène verte ou remontée avec chiffres.
9. **Dépendance T8** : quatre tests (`html-text` Ask × 3, `html-view` annotation) ne passent qu'avec le lecteur
   et l'annotation de T8 ; T9 les liste `n.a. → T8`, T8 les reprend.
